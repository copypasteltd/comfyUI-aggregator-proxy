# 79 · 网关模型目录持久发布协议

日期：2026-10-25（Asia/Taipei）。关联待办 01～04、47、72；规则 DEV-07、12、14、17、20、21、23、24、26、27、30～32。

## 1. 行为与兼容边界

控制面为每个 GatewayService 保存不可变的完整目录版本。管理员发布期望配置，Provider 使用自己的服务凭证主动拉取，校验本机账户/分组、持久保存配置、应用后提交回执。控制面仅在目标实例、版本、摘要及当前模型绑定全部匹配时记录确认；页面必须分别展示期望配置和已确认配置。

首次成功确认前保持 legacy 模式，现有启动文件和未携带目录版本的准入继续工作。首次确认后进入 managed 模式且不可自动退回 legacy；新准入必须携带已确认的 instance_id/revision/digest，并匹配当前主体的公开模型、Workflow 发布版本和价格版本。新的待同步版本不提前取代上一确认版本。空目录是有效的受控下架操作。

原请求幂等查询、确认/中止、关闭证明、已有任务和结算继续使用原身份与冻结记录。目录更新不能阻止已接收请求按原版本核对，也不能改写旧任务、原目标、已冻结金额或 Sub2API 账本。原生业务 Key 入口不受网关目录版本控制。

## 2. 冻结请求与预算

请求使用严格 DTO，拒绝额外字段。新增机器契约为 gateway-catalog-publication、gateway-catalog-replay、gateway-catalog-receipt、gateway-catalog-stamp 及内部配置 gateway-catalog-configuration；响应另由实现 OpenAPI 冻结。

发布包含 expected_revision（初始为 0）、instance_id，以及最多 256 条规则。规则包含十进制字符串 usage_account_id、group_ids、price_version、八位以内小数的正 unit_price，以及 1～64 个 model_bindings（model_id、expected_revision）。账户/分组 ID 限正 int64，避免浏览器整数精度损失。金额上限为 1,000,000；不使用浮点货币。

每条规则的模型绑定须具有相同别名、任务类型和默认参数；同一目录别名唯一，同一模型只出现一次。整个目录最多 512 个模型绑定和 4096 个分组引用。默认参数、租户/项目、模型 revision、Workflow 发布 ID/摘要和允许渠道从数据库生成，客户不能自报这些快照。模型必须已发布、Workflow 活跃、渠道已应用并验证且有运行批准，并至少有一个已启用且未排空的合格渠道。发布、确认与新准入都重新检查；该条件不声称 GPU 当前空闲或在线。这里只验证控制面事实；Provider 仍须验证其本地账户/分组和请求支持能力。

配置保存为 UTF-8 configuration_json，使用 canonical_json v1 的确定性序列化文本，digest 为该文本原始字节的 SHA-256（没有 fingerprint 的域前缀）。Provider 对传输文本直接验摘要，再严格解码。每个配置最多 512 KiB；管理历史每页 20 条摘要，单版本详情单独读取。状态响应至多携带期望与确认两份配置。拉取/回执另有每网关 120 RPM、20 burst 的预算。

## 3. 版本、回执、重试与回滚

每次发布、重试或回滚均在短数据库事务中创建新 revision，要求 If-Match、CSRF、models:publish 与 Idempotency-Key。相同管理请求重放返回原结果，正文不同返回冲突。不可变发布行禁止 UPDATE，且有指向网关和创建管理员的外键。

重试重新校验当前模型，并复制所选历史目录为新期望版本。回滚同样创建新版本，不移动旧指针、不直接修改 Sub2API 表。历史绑定的别名、Workflow、渠道和默认参数须仍与当前模型一致；若内容已变化，先显式恢复模型配置。重新发布可刷新当前模型 revision，但不能把不同内容冒充原历史目录。

回执绑定网关服务身份、固定 instance_id、revision 与 digest。状态为 applied 或 rejected；错误码来自固定集合，不能上传原始错误、凭证、地址或调用栈。重复相同回执不增加审计；rejected 可转为 applied，applied 不可降为 rejected。迟到的旧版本回执可以记录，但不能覆盖新的确认版本。Provider 只在响应 activated=true 后将该版本用于新请求；确认响应丢失时重放原回执。

applied 回执只确认当前期望版本，且再次检查绑定的模型 revision/发布内容、Workflow 活跃和渠道运行批准。已确认目录后续遇到模型变更时显示 stale；新准入按当前模型重新核对并拒绝过时绑定。重试/回滚/确认不会隐式发布模型或批准渠道。

## 4. 数据与事务

新增 gateway_catalogs（每网关唯一、期望 revision、确认 revision、instance_id）、gateway_catalog_releases（配置文本、摘要、来源 revision、动作、创建者）和 gateway_catalog_receipts（每版本唯一、结果、错误码、时间）。准入增加可空 catalog_revision/catalog_digest/catalog_instance_id，带复合外键及全空/全有检查；已有行保持 NULL，旧意图摘要保持原算法。带目录版本的新意图将 stamp 纳入摘要。目录 instance_id 一经创建即固定；更换逻辑实例须创建新的 GatewayService，凭证轮换不改变实例。

管理发布与确认先锁 GatewayService，再锁目录，随后按 UUID 排序读取模型及渠道。新网关准入在原请求幂等命中之后读取并共享锁定 GatewayService 和目录，再读取模型；目录版本校验处于任务与额度的同一事务。管理写对 GatewayService 使用 NO KEY UPDATE，避免准入 fence 的外键 KEY SHARE 导致锁升级死锁；新准入使用 SHARE。外部 HTTP 不在持锁事务内执行。

数据库迁移为向前兼容新增表/可空字段。迁移前原生 pg_dump 并验证目录；存在目录或 stamped 准入事实时禁止降级删除。旧 Provider 在 managed 启用后不能提交新的无版本任务，因此在完成消费者升级前不得确认启用。

## 5. Provider 与 Admin 后续接线要求

Provider 需在自身 PostgreSQL 保存应用版本及原始配置，使用有界、可停止的拉取循环；验证失败保留上一可用配置并提交固定拒绝码。请求使用不可变规则快照，持久意图保存其目录 stamp。已移除的模型别名保留受控归属记录，避免落入普通供应商路由。重启须恢复并核对目录，不能仅相信进程内映射。多进程使用同一实例名时各自仍须受已确认 revision 的准入栅栏约束；单实例回执不能宣称所有副本都健康。

Admin 要展示模型/规格/价格、期望与确认版本、摘要、差异、失败原因、历史、重试与回滚；响应丢失使用原幂等请求核对。变更页面后更新截图/GIF。仅交付控制面协议不得把 01～04 标记完成。

## 6. 验证要求与实际状态

验证须覆盖真实 PostgreSQL 的持久恢复、并发 CAS、应用/确认丢失、旧回执、错误网关/实例/摘要、绑定漂移、空目录下架、回滚内容检查、legacy 到 managed 切换、旧请求幂等与原账本恢复。另需 Provider 原生跨进程和 Admin 浏览器验证。

本专题先冻结协议，再实现。控制面、Provider、Admin 各层的实际通过范围与证据在交付记录追加；六类真实 Workflow、Redis/S3、设备规模和生产验证继续保留原待办。

## 7. 已实现接口与调用约定

| 方法与路径 | 身份/权限 | 行为 |
| --- | --- | --- |
| GET /admin/api/v1/gateways/{identifier}/catalog | 管理会话，models:read | 当前期望、确认、当前期望回执及绑定漂移状态 |
| GET /admin/api/v1/gateways/{identifier}/catalog/releases | 管理会话，models:read | page 从 1 开始，每页 20 条摘要，has_more 标记后续页 |
| GET /admin/api/v1/gateways/{identifier}/catalog/releases/{number} | 管理会话，models:read | 单个不可变配置及摘要 |
| POST /admin/api/v1/gateways/{identifier}/catalog/releases | 管理会话，models:publish | 201 创建期望目录；CSRF、If-Match、Idempotency-Key |
| POST /admin/api/v1/gateways/{identifier}/catalog/replay | 管理会话，models:publish | 201 创建 retry/rollback 新版本，沿用管理写保护 |
| GET /gateway/v1/catalog?instance_id=… | 独立网关服务身份 | 仅获取自己的目录；不要求客户委托头 |
| POST /gateway/v1/catalog/receipts | 独立网关服务身份 | 校验版本、摘要、实例与绑定，返回 receipt、activated 和 state |

初次发布的 expected_revision 为 0，If-Match 必须为带引号的 `"0"`。发布响应是不可变版本，不包含“已生效”承诺；随后读取状态或消费回执。同一管理幂等请求重放即使后来版本已变，也返回首次发布结果。写请求改变正文必须使用新的幂等键及当前 revision，不能在响应未知时自动换键。

state.status 的 legacy 表示尚无目录；pending/rejected/stale 与 managed 是独立维度。首次确认前 pending 仍是 managed=false；后续 pending/rejected 保持上一确认配置。stale 表示期望绑定不再满足当前控制面事实，confirmed_stale 单独说明上一确认配置是否也漂移。last_receipt 仅对应当前期望版本。applied 回执说明该实例声明完成应用，不是所有副本或实时运行健康的证明。

本轮没有新增图形入口或 Provider 自动消费者。当前 Provider 使用启动文件且不携带 catalog；在消费者完成之前手工提交首次 applied 将阻止它创建新任务。开发/测试可以使用明确的合成网关验证协议，生产接线继续按待办 01～04 实施。
