# 63 · 管理审计保留与有界清理

2026-10-24，第 63 增量。本地实现、原生清理/恢复、浏览器及精确候选安装验证通过；完整首版及真实设备范围不变。

## 保留策略与授权

原 180 天是设计初值，正式保留要求尚未确认。本轮实现可配置的管理审计清理能力，GEN_AUDIT_RETENTION_DAYS 缺省为 null，即不自动删除；明确配置 1～3,650 天并重启对应原生服务后才启用。生产保留期需由部署方确定，180 天仅为示例，不在开发机隐式启用。此设置独立于已有 GEN_ACCESS_LOG_RETENTION_DAYS，不删除客户访问记录、任务、计量账本、内容、Key、会话或 GPU 事实。

新增只读 GET /admin/api/v1/audit-retention，沿用管理会话和 audit:read；业务 Key、Worker/网关服务身份无权读取。响应在 contracts/admin-audit-retention.schema.json 冻结：enabled、retention_days、batch_limit=500、snapshot_at、last_batch。enabled 仅表示当前 API 配置；last_batch 是已提交清理事实，不表示 Runner 正在线。历史批次仍显示其当时的保留期，不能以当前配置改写历史。

## 清理事务

由持久 Runner 的维护周期调用，默认关闭时不访问清理事务。启用后单次至多 500 条，以原生 PostgreSQL UTC 时钟计算截止，只删除 created_at 严格早于截止的 audit_events。日期相等、新记录和未来记录保留；当前配置不受客户参数控制，读接口没有触发清理的副作用。

第 67 增量的完整回归发现，旧 DELETE 内嵌 LIMIT/行锁子查询在特定查询计划下会超出批次上限。必须在同一事务先读入至多 500 个已锁定 ID，再删除这一固定集合，避免依赖删除语句中的子查询求值次数；沿用原互斥、截止、跳过锁、预算与原子摘要。复现、修复和新候选验证见 [67](./67-Workflow失败目标重试与操作关联.md)。

每批使用固定事务 advisory lock，取不到锁即跳过；按 created_at/id 选择，FOR UPDATE SKIP LOCKED 避免等待被其他事务占用的行。事务设置 2 秒语句、250 毫秒锁预算。删除和 audit.retention_pruned 摘要及 outbox 在同一事务提交，失败回滚；摘要仅含实际条数、当时保留天数和截止，不包含被删除正文、凭证明文或任意客户资料。新摘要按当前时间记录，供后续审计；重启只处理仍存在的到期行，不能重复计算已删除批次。追加审计的保留期清理仅限本受控入口，不增加浏览器删除或任意数据库修复入口。

本轮不新增表/索引/迁移，沿用 0a7d9b4e2136 的 42 表和第 61 增量的创建时间索引。已有对象/数据库恢复命令可恢复原归档；生产执行清理前应落实既定备份与保留方案，过期删除不能依赖应用回退来恢复。

回退到尚不认识新增配置的版本前，先停止 Runner，移除 GEN_AUDIT_RETENTION_DAYS，并按既有发布流程切换应用；旧 Settings 会严格拒绝未知字段。本轮不执行数据库降级。关闭/回退不会找回已清理记录，既有安全摘要仍按原审计读取规则展示。

## Admin 与边界

审计页展示是否配置自动清理、天数、每批上限，以及最近已提交批次的时间/数量/截止。禁用时明确显示未启用；没有批次时显示尚未观察到清理。状态读取失败保留标明过期的最后成功状态，不显示为新事实；不能阻断审计列表的独立读取。复用原刷新、隐藏/注销/离页取消与角色检查，不新增后台轮询或续期行为。

图片、视频、ComfyUI Workflow 音频与其渠道、任务、配额和内容均保持原协议。正式保留政策、生产部署及真实资源仍待独立验收。
