# 149 · 未知内存回收维护占用核对

本次用户明确要求清理 RTX 4090 的遗留维护占用。ComfyUI 在线、源队列为空，平台生成占用为空；原操作因 `/free` 响应丢失进入 `unknown`，不能靠刷新、超时或直接改表解除。

## 固定维护动作与开发约束

新增本机运维命令 `python -m generation_infrastructure.memory_reconciliation --operation mmo_UUID`，默认只检查；显式 `--apply` 才执行。命令读取既有受保护的服务环境，不接受任意 URL、图、SQL 或 shell；不增加业务或 Admin 的强制解锁入口，不改变数据库结构与现有 API。适用 DEV-07/08/09/23/25/26/27/29。

1. 只接管指定的未知内存回收操作；验证策略仍指向它、地址和物理 GPU/渠道分组与原快照相符，全部维护锁仍属原操作。采用原调度全局锁、GPU 行锁及有界操作租约。
2. 拒绝真实任务、未归还/未知生成占用、其他维护锁、原生面板预约、过期 Worker 心跳，以及不支持的 ComfyUI 版本。HTTP 均在事务之外。
3. 记录当前 Worker 启动快照。后续步骤中启动或配置变化即停止；原快照与当前快照不同可以记录，但不能忽略本轮中的变化。
4. 保留原 `/free` 的不确定性，**不重发 `/free`**。在现有维护占用下，依次提交两个固定 `EmptyImage(1×1) → PreviewImage` CPU 屏障；每次提交前保存独立关联标识和意图，提交响应丢失只查原关联，不重投。
5. 核对两次实际 history 的图、关联标识、成功终态和提交顺序；末次源队列为空，并在最终事务内重新验证所有权、心跳、启动、配置及无业务活动，才原子归还本操作的维护锁。
6. 原操作记作 `skipped` 并保留原错误、恢复证明与审计；`released=false`，不会把未知 `/free` 写成已确认卸载。策略重新开始原有空闲倒计时。重复运行只返回原收尾结果；无法证明时继续保留锁。

两个屏障只证明串行执行循环已越过原维护时段，不承诺 RAM/VRAM 归零。最多产生两张 1×1 临时预览，不操作客户文件、历史、模型或进程；不重启 Windows/ComfyUI/平台服务。已记录的屏障意图不可因超时清空或重新提交。
