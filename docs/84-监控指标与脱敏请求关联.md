## 1. 入口与身份

新增 `GET /internal/monitoring/v1/metrics`（Prometheus text 0.0.4）和 `GET /internal/monitoring/v1/configuration`（安全配置 JSON）。默认未配置凭证，返回 404；启用后同时检查 Bearer 与实际连接来源 CIDR，拒绝时不查询数据库。监控凭证形如 `mon_<32 hex>.<43 URL-safe>`，部署仅保存完整 token 的 SHA-256，常量时间比较，最多两把支持轮换。它只读本节两个入口，不能生成、下载、修改配置或调用管理/Worker/网关接口；原四类身份也不能调用监控接口。

`GEN_MONITORING_TOKEN_SHA256` 为 JSON 数组，缺省 `[]`；`GEN_MONITORING_ALLOWED_NETWORKS` 缺省 `["127.0.0.1/32","::1/128"]`。只采用 ASGI 实际 client，禁止相信任意 X-Forwarded-For。反向代理需显式配置可信代理，并在网络层限制监控源；生产使用 HTTPS。配置响应不返回 token、摘要、DSN、文件路径、客户/节点/渠道标识或原始样本，只返回凭证槽数量、来源网段数量、固定预算和告警阈值。

原生 CLI `gen-monitoring issue-token --output <private-file>` 以排他创建写入一次性凭证文件，仅输出 SHA-256；不得覆盖文件或打印 token。`configuration` 输出部署配置投影，`rules --output <new-file>` 生成同一阈值的 Prometheus rule JSON（JSON 是 YAML 子集），不连接业务数据库。部署者负责文件 ACL、令牌分发、轮换和采集端安装，不自动注册外部服务。

`configuration` 与 `rules` 支持 `--env-file <explicit-private-file>`，供隔离安装和外部状态目录使用；环境变量按 Settings 既有优先级覆盖文件。错误只输出固定失败码，不展开含凭证的配置校验异常。HTTP 观测位于完整 FastAPI 错误处理栈之外，500 响应的头、字节和服务端请求 ID 也必须可关联，原异常仍向服务器传播。

## 2. 指标和日志语义

每个 API 进程有独立 registry、启动时间、CPU 时间、HTTP 请求/在途/字节、响应头等待及完整响应时长 histogram。HTTP 只按固定操作组、方法、状态类别、完成状态及拒绝类别聚合；不使用请求 URL、查询串、异常文本、job/key/tenant/model/节点/渠道 ID 作为标签。操作组固定为 health、admin_read、admin_write、business_read、business_write、gateway_read、gateway_write、worker_read、worker_write、monitoring、admin_static、other。请求 ID 只进入有界 JSON 日志和既有访问/审计关联，不进入指标标签。

纯 ASGI 包装只观测流经的 body 字节，不能缓存内容、预读上传、提前结束 SSE、吞掉取消或更改背压；响应头等待和长流持续时间分别统计。日志仅含固定事件名、服务端 UUID、注册路由模板/固定未知桶、方法、状态、完成类型、时长和字节。启动入口关闭 Uvicorn 原始访问日志，统一使用该脱敏日志；堆栈、请求正文、凭证、cookie、路径参数与查询串不得出现在该事件内。日志输出/轮转由宿主收集，日志故障不改变业务结果。

数据库快照从 PostgreSQL 权威事实聚合：活动任务按状态/六类能力/客户或验证分组，队列/准入/重试/核对年龄与候选覆盖，最近一小时终态与固定失败分类、有效端到端 P50/P95/样本数，物理 GPU held/uncertain/管理保留，节点心跳与容量覆盖、渠道配置/观测、规格隔离、待投递 outbox 与结算年龄、待删对象数量/字节/年龄，以及 PG 连接和锁等待。不展开共享候选，不将同 GPU 多渠道计为多个 GPU。未知执行和过期租约不能导出为可用 GPU。

最近窗口指标均为 gauge，进程计数才是 counter；历史过期可下降。作业时长仅接受 accepted_at <= terminal_at <= 当前时刻，不表示 GPU 推理耗时、费用或 ETA。未来任务时间单独计为 jobs_age_unknown，无有效时间时省略该组等待年龄，不伪造零等待。容量使用既有 boot/15 秒新鲜度/严格 WorkerCapacity 校验；无效、过期、缺失样本为 unknown，不能作为健康或零压力。最多读取 256 个启用节点、每份容量 JSON 至多 8192 字节；超界明确使快照不可用。只投影容量子树，不读取模型/工作流清单。

## 3. 预算、失效和数据库索引

每个进程专用只读数据库池：pool_size=1、max_overflow=0、pool_timeout=0.1 秒、connect_timeout=1 秒；不能占用业务池。REPEATABLE READ + READ ONLY，无行锁和业务写入。快照 SQL 总预算 2 秒，每条语句最多 1 秒、锁等待最多 100 毫秒；连接准备最多额外 1 秒。单并发刷新、5 秒缓存；并发刷新不等待业务锁，超时/忙碌/失败时省略全部数据库 gauge，并输出 snapshot_success=0 与最后成功时间，不能将旧数据伪装为当前值。HTTP/进程指标继续可读。exposition 最大 2 MiB，溢出固定 503，不回显数据。

新增可向前兼容迁移 `3da02e7b5941`，父版本 `2c9f1d6a4830`：活动任务部分索引、最近终态时间覆盖索引、未投递 outbox 年龄索引和待删对象年龄索引，不增加业务表或改任务状态。迁移仍先备份验证、维护窗口执行，不能声称索引创建无生产阻塞。

## 4. 配置与外部告警

`GEN_MONITORING_THRESHOLDS` 为严格 JSON 对象，字段见 [配置契约](./contracts/monitoring-configuration.schema.json)。默认 queue_age_seconds=300、pending_age_seconds=60、settlement_age_seconds=300、node_stale_seconds=30、http_error_ratio=0.05、minimum_requests=20、alert_for_seconds=120。阈值变更通过部署配置与重启生效；配置 API 只读，生成规则与响应来自同一模型。

规则覆盖采集目标不可达、DB 快照失败、队列/准入老化、任务时钟异常、未知 GPU、节点心跳过期、容量未知/压力、结算积压与 HTTP 5xx 比例（最低请求数门槛）。宿主配置示例放 app/deploy/observability，令牌使用 credentials_file，TLS 证书校验保持开启，不提供不安全跳过开关。多 API 实例 HTTP counter 按实例抓取后聚合；全局 PG gauge 用 max 去重，禁止 sum 多份相同快照。Admin 现有固定命名派生告警保持其既有语义；这套阈值属于外部采集规则，不能冒称已修改 Admin 页面或部署了通知服务。

指标命名、counter/gauge 和低基数约束依据 [Prometheus 命名规范](https://prometheus.io/docs/practices/naming/)；自定义采集使用 [官方 Python client](https://prometheus.github.io/client_python/collector/custom/)，冻结依赖 prometheus-client 0.26.0。不得注册会暴露环境或无界标签的默认 collector。

## 6. 原生操作顺序

1. 在私密状态目录运行 `gen-monitoring issue-token --output <new-private-file>`，只把输出的 SHA-256 放入 `GEN_MONITORING_TOKEN_SHA256` 数组；原 token 文件分发给采集端，并由宿主 ACL 限制读取。
2. 在控制面显式配置允许的连接来源和严格阈值，重启受托管的 API；先核对无凭证/错凭证拒绝，再从获准来源读取安全配置和 metrics。反向代理不能把任意客户端转成获准来源；代理入口和头信任需单独限制。
3. 用同一私密配置运行 `gen-monitoring configuration --env-file <private-env-file>` 与 `gen-monitoring rules --env-file <private-env-file> --output <new-rules-file>`；配置示例见 [monitoring.env.example](../app/deploy/observability/monitoring.env.example)。命令不启动采集服务，不连接业务数据库。
4. 根据 [Prometheus 示例](../app/deploy/observability/prometheus.example.yml) 配置 CA、credentials_file 和每个 API 进程的独立采集目标；同一控制面数据库使用同一采集 job。多个进程若被负载均衡成一个抓取目标，会漏掉进程级 HTTP counter，因此每个进程必须可分别采集。
5. 使用已校验的原生 promtool 检查生成规则，再由宿主部署采集、日志收集与通知。轮换时最多同时配置两个摘要，确认新凭证生效后删除旧摘要；运行中日志失败只增加 dropped 计数，不改变客户响应。
