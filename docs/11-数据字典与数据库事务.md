## 1. 通用字段与归属

数据库主键采用 UUID v4；公开 ID 为类型前缀加 UUID 的不透明文本，映射见文档 12。时间列为 `timestamptz`，权威判断使用数据库 UTC 时间；版本计数为正整数，字节/毫秒/计量使用 bigint 或明确精度的 numeric，金额不得 float。SHA-256 为 64 位小写十六进制。所有可编辑配置具有 revision、created_at、updated_at、created_by、archived_at。

租户资源强制 tenant_id；项目资源带 project_id；业务任务、素材、产物带稳定 owner_key_id。租户/项目/Key 的复合外键校验归属，例如项目 `(tenant_id,id)` 唯一、job 以 `(tenant_id,project_id)` 引用项目；任何跨租户绑定都应在数据库层失败。UUID 的不可猜测性不替代授权。平台物理设备由管理面登记，通过授权绑定关联租户公开能力，不因为设备为平台资源而放宽客户数据权限。

大 JSON 用于冻结参数/依赖清单/脱敏事件，不承载需要检索和互斥约束的核心状态。图片视频不入库；历史 attempt、计量、绑定和审计不物理级联删除。

## 3. 数据库强约束

下列是需要迁移实现的约束清单，不提供可直接对现有库执行的半成品 SQL：

1. `jobs.current_attempt_id` 与 `job_attempts(job_id,id)` 使用复合引用；当前结果权只能属于同一 job。attempt_no 单调增加，fencing_token 每次结果权重新授予增加，不能重置为 1。
2. `gpu_occupancies(gpu_id)` 唯一保证生成槽位；上传中的 attempt 仍有效，但不再持有该行。**不能建立“所有未结束 attempt 在 gpu_id 上唯一”的索引**，否则第一份产物上传时无法执行下一任务。
3. 终态与 ended_at 一致；manifest 发布只允许 succeeded 的同一 current_attempt。先 CAS 终态，再写唯一结算/outbox，同一事务提交，竞争失败返回既有结果。
4. 资源计数有 CHECK 非负与 reserved+consumed 不超当前可预留上限的事务校验；收紧低于已用量允许保存，但后续新增预留应被拒绝，不能修改历史已用量以满足 CHECK。
5. API Key 凭证、session、渠道 secret 引用分别存储；渠道秘密需要可解密调用，使用受保护主密钥加密或外部 secret store，绝不与客户 Key 的不可逆 verifier 混用。
6. 逻辑删除不影响历史外键。GC 必须同时检查对象状态、retain_until、活动输入引用和上传确认；内容项删除只标记源生命周期，不修改 job 成功历史。

## 4. 一致的锁顺序

事务统一顺序：幂等记录/准入意图 → 配额主体（tenant、project、key；同级 UUID 排序）→ job（UUID 排序）→ GPU（UUID 排序）→ attempt/对象 → 审计和 outbox。代码复用一个锁规划器，禁止某入口反向取得这些锁。纯观测心跳只追加观测，不顺手释放槽位。

领取先无锁读取候选与其主体，再按顺序锁配额、`FOR UPDATE SKIP LOCKED` 锁 job、最后锁 GPU，并重新检查所有条件；候选失效立即短路，不能长时间等锁后执行旧计划。事务仅做本地数据库工作；不得在锁内下载文件、调用 ComfyUI、存储、网关或等待 Worker。

READ COMMITTED + 显式行锁/CAS 为首版基线。唯一冲突、死锁和序列化失败仅在“整个事务可幂等重放”时做有界退避重试；不能捕获异常后只重跑半段扣配额。每个并发用例独立 Session。

2026-10-22 并发实现补充：幂等行写入会对父 Key 持有外键 KEY SHARE。Key 的策略、启停和 revision 变更不修改主键，统一使用 `FOR NO KEY UPDATE` 序列化，不能再将父 Key 升为与 KEY SHARE 冲突的 `FOR UPDATE`；否则不同幂等请求先持有外键锁、再等待同一配额桶时会形成死锁。资产准入/删除与 GC 的引用锁、跨日准入和实际表映射分别见文档 20、21；新增测试必须覆盖不同幂等键的真实 PG 并发，不能只测同一幂等键重放。

## 5. 关键事务流程

### 5.1 准入与幂等

鉴权、基本输入上限及当前访问权限检查后，根据逻辑 key_id、规范操作 `generation.create` 和 Idempotency-Key 查映射。`request_fingerprint` 仅包含规范公开语义：模型别名字符串、task_type、显式参数及参数是否提供、素材内容哈希/角色/顺序、schema_revision。排除随机 multipart 边界、URL 签名、轮询方式、请求 ID、client_request_id、首次自动 seed 和首次解析出的别名目标。

已有映射：按该记录的规范化版本比较相同语义；相同返回原 job，不再解析当前别名或抽 seed，不再预留额度，但仍检查当前调用身份/可见范围。缺少 `jobs:create` 的调用者不能借重放创建入口绕过操作权限，可按已授权查询接口取结果。不同语义 409。

首次请求：解析别名和具体发布版本、校验素材授权与 ready、确定 seed，生成 `execution_fingerprint`（含冻结发布/参数/内容哈希/seed），原子写入 job、幂等映射、未完成与资源预留、job_event/outbox。每日 accepted 计数在正式准入转换时记入服务器时间对应的 Asia/Taipei 自然日；内部重试沿用同一 job，不重计。无幂等键每次创建新 job。

摘要序列化必须有独立canonicalization_version：对象键排序、数组保序、UTF-8编码、十进制数规范化，不改写提示词Unicode码点、不以浮点四舍五入改变语义；保留参数“省略/显式指定”信息。基于校验后的素材内容摘要，不使用临时URL/文件名。重放使用原规范化版本，升级后保留旧版本比较器到幂等窗口结束，不能将所有旧记录作废。

跨网关准入：先建立 admission_pending 与有期限预留，不能派单；网关完成额度/公共 ID 确认后用幂等 confirm 转 queued。过期与 confirm 竞争通过同一 intent 行锁裁决，过期者拒绝后到 confirm 并走网关释放/对账。跨日时以最终 queued 的 accepted_at 归日，必须在转换事务重新检查当日 accepted 计数；失败则释放预留，不能先派单再补记。两个系统不做伪分布式数据库事务，外部步骤走 outbox/inbox 对账。

### 5.2 领取生成槽

按锁顺序取得当前 Key/项目/租户并发计数、queued/retry_wait job 和空闲物理 GPU。核查冻结路由、当前资源上限、applied/verified 环境、维护/排空、deadline、节点/boot 恢复状态以及输入仍可用，建立 attempt、增加 fencing、写 occupancy、CAS job→leased、增加 generating 计数和事件，提交后返回租约。

每次领取请求带唯一 request_id；成功领取映射与 attempt 同事务保存。响应丢失时重复 request_id 返回同一租约，不再取第二份。空队列 204 可短暂重用，不长期阻塞后续领取；请求 ID 生命周期与重放规则见文档 12。下发前不向数据库锁外的 Worker 预先承诺槽位。

### 5.3 更新、释放 GPU 与继续回传

事件先检查 node、boot、attempt、fencing、当前结果权和事件去重，再使用 state_version 更新。确认生成/所有 GPU 编码结束且本地输出稳定后，以 `gpu_released` 事件原子删除对应 occupancy、减少 generating、记录 GPU 释放证据、推进 uploading；job 当前 attempt 和结果租约继续有效。重复释放不能再次减数。

如果事件到达时租约已过期，普通状态更新被拒绝，交给 reconcile 端点校验恢复证据；不能用迟到 event 自动复活权利。失联时保留/转换 occupancy 为 unknown，不因期限经过删除；若 GPU 早已确认释放则只核对上传结果，不重新占槽。

### 5.4 完成、计量与结算

Worker 上报不可变对象 key/version/hash 清单；云端在事务外读取并验证存储和媒体，然后在短事务中重新检查 job 状态/current_attempt/fence、所有对象验证结果与输入引用，写 manifest、CAS succeeded、完成预留/实测计量、写结算和 outbox。外部账本尚未确认时 `billing_status=pending`，不伪报 settled。

产物实际规格超出购买/预留时暂停验证并报错处理，不能多扣钱后当作已同意的扩容。失败/取消释放尚未消费的资源预留和未完成计数；accepted 每日任务计数不退；已确认 GPU 计算结束才减 generating。重复 complete 返回已确认 manifest；旧 attempt 写来的对象作为未发布对象等待清理，不改变现有成功。

### 5.5 管理配置与异步操作

If-Match 校验 revision 后，同事务更新 desired revision、写审计与 management_operation/命令 outbox。Worker 回执 applied_revision 与实际环境摘要；验证通过后单独批准 binding。不能以“消息已发出”设置 applied/verified。批量目标各自有结果，跨渠道无需伪装全局原子成功。

冻结运行中的 channel_revision、workflow_release 和 input 不可更改。修改凭证/地址/依赖时先保存新 desired，旧任务按冻结快照收尾；会破坏在途执行的变更必须排空。平台主密钥失效/安全隔离可中止访问，但必须显式记录并按状态机处理。

### 5.6 Outbox 与列表快照

Outbox 在业务事务中落盘；发送者先短事务领取发送租约，提交后 HTTP 发送，再幂等确认，不跨网络持有数据库锁。重试次数/退避/死信与告警有上限，不因死信删除原记录。

数据库序列号分配顺序不等于事务提交顺序，不能把 `max(bigserial)` 直接当成无缝快照水位。首版 Admin SSE 使用**失效通知后重取一致快照**：单个队列快照在同一 REPEATABLE READ 事务取得统计与列表首屏；客户端连 SSE 成功后再拉快照，期间通知合并为 dirty 并在响应后补拉。重连、发现间断或超过 5 秒未确认新水位均重取快照；SSE 不在前端直接增减计数。其 cursor 仅为已发布通知游标，不能用于跳过未提交业务事务；服务端额外的 5 秒检查保证 outbox 延迟后修正。这样保留实时更新目标，避免伪造精确增量一致性。
