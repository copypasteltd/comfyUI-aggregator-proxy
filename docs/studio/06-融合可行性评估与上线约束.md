# 06 · 融合可行性评估与上线约束

## 1. 结论和交付目标

**可以融合，但原版不能直接作为最终可用的融合产品上线。** 推荐继续采用 React 画布作为创作前端，复用现有中转服务的持久任务、业务 Key、Workflow 发布、GPU 调度和内容交付。需增加专用适配器、可靠提交日志及媒体节点，并补齐安装、移动端、主题和部署问题。本文矩阵记录评估基线；正式分支的最新实现和验收见 [10 · 开发进度](10-开发进度与交付记录.md)。

本次评估增加了真实的原生安装尝试、隔离修复验证和离线协议检查；运行结果统一见 [08 · 验证记录](08-可用性验证与发布验收.md)。方案契约和故障处理见 [07](07-融合实现契约与故障恢复.md)。之前 [04](04-本地源码与中转服务融合方案.md)、[05](05-中转服务接口映射与开发验收清单.md) 的初步设计继续适用，下列发现补充并修正其不足。

融合版首期目标是：用户拿到一个有相应授权的业务 Key 后，在桌面或手机 Web 中选择真实可用的模型，上传必要参考，提交、离开和恢复任务，最终保存图片、视频、Workflow 音频或 GLB。管理者继续通过 Admin 管理渠道、发布、Key 和队列。完整首期必须通过本文和文档 08 的全部适用验收项。

以下能力独立说明：首期有 GLB 交付卡，交互三维预览另验；本机画布与可选 WebDAV 不等于服务端账号或多人实时协作；Workflow 音频不等于 TTS；原有 10～20 台设备目标不因画布接入而自动获得容量签收。

## 2. 选择的架构

| 方案 | 优点 | 代价/问题 | 结论 |
| --- | --- | --- | --- |
| 只配置 OpenAI Base URL | 配置简单 | 已确认字段、音频、3D 和恢复协议不匹配 | 无法满足完整目标 |
| 每个模型维护调用脚本 | 易于临时试通 | 任务记录、恢复、授权下载分散；脚本在页面权限下执行 | 不作为正式融合路径 |
| 画布专用中转适配器 + 原服务 | 同一任务协议覆盖七种任务类型，保持轻量静态部署 | 需完成前端改造和少量明确的服务接口加固 | **采用** |
| 再建画布生成后端/第二套队列 | 可自定义全部行为 | 重复授权、配额、任务和恢复责任，增加部署成本 | 当前无必要 |
| 直接把 React 组件嵌进 Vue Admin | 一个页面框架入口 | 状态/依赖/样式耦合大，不能替代接口适配 | 分别构建、统一导航与视觉 |

部署目标保持现有高位 HTTP 服务，新增 `/studio/` 静态入口；`/admin/` 与 `/v1/` 分别保留管理和业务接口，CORS 继续允许任意源。浏览器直接使用业务 Bearer 调用，不要求增加常驻 Agent、Redis 或第二套数据库。

开发路径继续遵守用户约束：画布代码、文档、工具和实验都在 `无限画布/` 内。需要正式实现服务端发布校验等后端补丁时，也在此目录内建立原中转仓库的独立工作副本/分支，沿用其发布规则和远端；当前相邻服务仓库仅作为只读依据，不移动或改写既有部署。

“同站点”包含信任关系：受托管模式不得运行用户导入的任意模型脚本或远程插件。原版插件并非权限沙箱，且本地插件发现阶段会先执行代码以读取元数据，即使显示为未启用也不能当成完全未执行。仅隐藏安装按钮无法满足要求，详见 07。

## 3. 已确认的新发现

| 编号 | 发现和影响 | 处理决定 |
| --- | --- | --- |
| R-01 | 原版 `npm ci` 失败：Pro Components peer 要求 antd 5；类型检查另发现 Modal 样式仍用旧 content 字段 | 隔离移除仅作包装的 ProConfigProvider/依赖，保留 antd ConfigProvider；Modal 改用 v6 container，经类型检查通过 |
| R-02 | npm 锁根缺 `i18next`、`react-i18next`，安装后还缺 Windows 原生构建包 | 更新锁并补齐精确匹配当前父包的 Windows 原生依赖；构建和干净安装分别验证，不跳过 peer |
| R-03 | 画布保存有 400ms 延迟，底层适配器存在 localStorage 回退 | 提交日志用独立可靠事务，必须等写入成功再 POST；不借用画布自动保存当日志 |
| R-04 | 单图/3D 的 `exact_reference_count=0`，但 slots/Schema 要求 `source_image` | 按槽位和 Schema 渲染，参考数组数量不能代替源图要求 |
| R-05 | 音频 preset 含格式/采样率等输出规格，任务参数未必允许同名字段 | 请求参数严格取 Schema 中的字段，完整 preset 用于选择与显示 |
| R-06 | 业务鉴权路径会消耗 Key 频率预算，查询也在其中 | 多节点/工作台共享轮询和预算，避免每个组件独立轮询耗尽 RPM |
| R-07 | 当前创建任务没有公开的“预期发布摘要”前置条件 | 新适配增加服务端发布摘要校验；发现后模型被重绑时明确 409，不能静默执行另一发布 |
| R-08 | 当前下载需要 Authorization，普通图片/播放器 URL 不会自动携带业务 Key | 从固定内容接口受鉴权获取，校验后变成本地资源；不往 URL 放业务 Key |
| R-09 | 原版插件使用 Blob import，模型脚本使用 new Function；管理 cookie path 不能隔离同源 JS | 受托管模式从运行入口拒绝任意代码、导入脚本及开发插件；保留经审阅的内置媒体实现 |
| R-10 | 普通远端 HTTP 与 localhost 的浏览器能力不同 | 幂等 ID 沿用 nanoid；SHA-256 采用支持普通 HTTP 的成熟增量实现，不能依赖 crypto.subtle |
| R-11 | 本地浏览器数据会受配额、用户清理和浏览器回收影响 | “已存本机”与永久备份分开；提供可恢复任务清单和明确导出/另存，不假装 IndexedDB 永不丢失 |
| R-12 | 大 GLB/视频全量 Blob、解码和重复副本会增加手机内存压力 | 只按需加载和解码，真实文件验证内存；超出已验证能力时可查看任务/元数据并明确转桌面保存，不承诺所有手机支持服务端最大文件 |

R-03、R-04、R-05、R-06、R-07、R-09 来自本地源码；R-01 为实际安装失败。R-10 的浏览器能力边界见 [MDN Crypto](https://developer.mozilla.org/en-US/docs/Web/API/Crypto)，增量实现候选见 [noble-hashes](https://github.com/paulmillr/noble-hashes)。R-11 见 [MDN 存储配额与回收](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)。候选依赖需在正式分支锁定版本并验证；本次没有将它加入原版。

## 5. 数据、身份和能力边界的决定

| 决策 | 采用内容 | 原因 |
| --- | --- | --- |
| 用户入口 | 个人业务 Key / 同源或指定中转源站 | 复用已授权的生成/内容体系 |
| 任务权威 | 服务端 PostgreSQL 任务状态 | 浏览器关闭不能等于任务停止 |
| 前端恢复 | 独立、立即提交的本机日志 + 服务端幂等 | 画布自动保存和内存结果不足以保证恢复 |
| 参数标准 | 服务实时自描述，完整 preset + JSON Schema 2020-12 | 包括 prefixItems、条件约束，不能用旧 Schema 校验器忽略它们 |
| 参考输入 | slots + request_schema 为准 | 源图与 references 数量含义不同 |
| 文件 | 服务校验媒体；浏览器验证传输字节/hash，按真实 MIME 展示 | 不把浏览器转码/后缀改名当兼容 |
| 任意代码 | 首期托管模式拒绝用户脚本和远程插件执行 | 同源 Admin 和本机 Key 具有真实信任边界 |
| 内容保留 | 云端成功后 8 小时，本地副本独立 | 与原服务约束一致，保证用户能解释结果为何失效 |
| 首期部署 | 现有高位 HTTP + 任意源 CORS + 静态 studio | 不引入新后端，不改变用户反代安排 |

新方案中唯一明确需要现有业务接口加固的核心项是 F-19 的发布前置条件；这是计划，并未修改当前 API。大文件原生下载票据、云端画布账号等扩展不冒充已有接口，确需扩大产品承诺时再独立设计和验证。

原有后台目标也保留：源副本移交即删、十分钟空闲回收和均衡模型池分别依据原项目 [121](../121-ComfyUI原始产物移交即清理设计.md)、[123](../123-空闲资源释放与多设备模型池调度设计.md)。当前代码或目录支持多渠道不等于均衡策略已实现，查询、画布保活和下载也不应重置生成空闲计时。画布只展示获准的状态；管理动作仍归 Admin，不让业务 Key 直接调用设备 `/free`。

## 7. 完成标准

“评估完成”表示架构、接口差异、开发范围和可复现验证已写清；“最终可用”须满足文档 08 的发布条件。当前发布判定为 **HOLD：融合未实现，尚不能签收最终可用**。

当有已发布模型暂不可用时，该媒体的端到端验收仍保持未完成，不能用其他模型截图或离线 Schema 通过替代。现有上游原版、隔离修复副本和未来正式融合分支始终分别标注，不能用修复副本构建通过证明原版安装通过。
