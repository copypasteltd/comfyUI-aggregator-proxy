# 129 · 三维兼容复查与 GLB 边界修复

日期：2026-10-29。复查对象为 128 的原生 3D 接入、既有六类媒体任务及真实 3080 TRELLIS2。本文分别记录源码复现、回归、安装字节和实际 API 调用；不扩大到其他 3D 格式或完整产品验收。

## 1. 复查发现

| 编号 | 触发条件与原行为 | 修复 |
| --- | --- | --- |
| F01 | 一个 accessor 先被作为自定义顶点属性检查，再被另一 primitive 用作 POSITION。通用已检查集合会使后者跳过位置计数和几何上限；6 个顶点被计为 3，测试上限 5 时也未拒绝。 | 单独记录已检查的位置 accessor；位置计数、坐标范围和几何上限不由属性检查缓存代替。共享同一 POSITION 的正常引用继续去重。 |
| F02 | 默认场景之外存在循环节点，或 scene.nodes 将某节点的子节点当成根。只遍历默认场景使这些文件被接受。 | 核对所有场景的根节点，遍历整个节点森林，并检查所有节点均被覆盖；保持深度和数量上限，合法的非默认场景仍可通过。 |
| F03 | 仅有 jobs:create / meshes:create 的 Key，经真实 HTTP 提交 image_to_3d 返回 403，额外要求 images:create。原有仓储层映射正确，但应用层的 preflight/create 仍将 3D 当作图片；此前测试 Key 同时有图片权限，未覆盖此缺口。 | 应用层两个入口使用领域媒体类型映射到独立 meshes:create；补充七类任务的最小权限、缺少必要权限的拒绝，以及实际 HTTP 上传/提交/幂等与图片权限不能替代 3D 的检查。 |
| F04 | 新业务任务实际生成并完整下载成功，文件大小/摘要正确，但通用 Content-Disposition 文件名只有平台 ID，没有 .glb，浏览器保存后不易识别。已有下载客户端会按 MIME 补后缀，未覆盖浏览器直接保存的情况。 | 对已验证的 model/gltf-binary 产物，在安全平台 ID 后固定追加 .glb；完整 GET、HEAD、Range 共用同一下载元数据，继续使用原鉴权、MIME 和字节读取。 |

四个初始场景在旧实现均复现失败。上一轮的有效 TRELLIS2 生成没有覆盖这些结构边界；旧报告保留，不将新增反例写成此前已经通过。补充反例包括另一个场景的错误根节点，以及合法的非默认场景。

F03 在本次 129.1 云端就绪后，以仅一件 3D 额度的临时 Key 实测发现，[线上原始错误的脱敏记录](evidence/2026-10-29/model3d-minimal-key-reproduction-129.json)保留。随后在未修复的应用层本地复现 5 项失败、15 项通过，包括 HTTP 正例的相同 403；不通过给 Key 增加图片权限绕开。该拒绝未创建生成任务，后续沿用同一个请求和幂等标识验证修复。

依据 [Khronos glTF 2.0 场景与节点规则](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#scenes)：节点层级必须无环且每个节点最多一个父节点，scene.nodes 只能列根节点。自定义属性使用下划线语义，复现样本使用合法 stride；这里只执行已声明的有限静态 GLB 交付校验，不声称实现 Khronos 的全部验证器。
