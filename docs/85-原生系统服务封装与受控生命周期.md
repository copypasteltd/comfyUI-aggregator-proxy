# 85 · 原生系统服务封装与受控生命周期

2026-10-25 冻结设计，关联待办 66、67、71、73；实现及分层验证在本文末尾记录。目标是为当前 Windows amd64 / CPython 3.13 发行包提供固定角色的系统服务部署工具。云端宿主尚未选定；若选 Linux，需要另外交付并验收 Linux 原生包和 systemd，不能将 Windows 候选改名后运行。禁止 Docker、WSL、VM，禁止隐式安装服务、提权、改防火墙或启动 ComfyUI。

## 1. 固定角色与边界

| 角色 | 实际启动目标 | 状态及配置 |
| --- | --- | --- |
| api | 安装目录 venv 的专用 `python-service.exe -I` + `release-entrypoint.py api` | 外部 env、独立状态目录、显式 HTTPS 证书及监听；HTTP 优雅关闭预算 90 秒 |
| runner | 同一已校验入口的 runner | 外部 env、独立状态目录；停止后保留数据库任务、outbox、租约 |
| gc | 同一已校验入口的 gc | 外部 env、独立状态目录；正常批次有界结束，不在服务注册时执行清理 |
| worker | 同一已校验入口的 worker | 外部 JSON、持久 journal/spool、独立凭证；ComfyUI 是单独维护的进程 |
| gateway | 安装入口 gateway → 包内固定 `gateway/sub2api-provider.exe` | 外部 Provider JSON、显式原生 `config.yaml`、`DATA_DIR`；不在 XML 写入数据库密码、业务 Key 或 JWT |

部署工具只生成和执行这些固定目标，不接受 shell、任意可执行文件、下载、远程指令、用户输入的参数列表或 reboot 恢复动作。业务 Key/Admin/Worker/网关/监控身份均保持原边界；操作系统服务账户不是新业务身份。DEV-01～03/05/09～11/19/25～27/30～32 继续适用。服务停止不等于业务排空；升级前仍按文档 15 排空，核对未知 GPU 和唯一产物。

## 2. 离线部署契约

封闭 JSON 见 [service-deployment.schema.json](./contracts/service-deployment.schema.json)。版本 `native-services-v1`；`deployment_id` 限 1～24 个小写字母、数字、连字符，首尾为字母或数字。最多 24 个服务，每项包含固定 role、instance、外部 config/state_dir 和 startup。`instance` 同样限制在 1～24 字符。服务名固定为 `rc-{deployment_id}-{role}-{instance}`，同部署不得重复，状态目录不得重叠。只支持本机盘符绝对路径，不接受 UNC、设备路径、相对路径、控制字符、环境变量展开、引号或重解析点。

API 额外必填 `listen`：IPv4/IPv6 字面地址、端口、外部证书和私钥；非 loopback 要显式 `allow_network_bind: true`。gateway 额外必填 `native_config`，作为 `CONFIG_FILE`；不依赖 cwd 搜索其他 YAML。其他角色不得带入这些字段。文件内容继续由各角色启动验证；部署检查不承诺数据库、网关、TLS 身份或模型已经可用。

所有角色的 installation、state、config、TLS 文件与部署输出分开；安装包保持不可变，状态与秘密在包外。渲染只写全新部署目录及指定状态目录下的服务日志/临时子目录，不覆盖旧部署、秘密或 journal。生成物保存规范化 spec、包清单摘要、wrapper/XML 哈希和 ACL 需求清单。验证时重新核对发行包、固定 wrapper pin、XML 的确定性重建及所有文件，拒绝额外/篡改文件；不能仅相信可编辑的部署清单。

## 3. Wrapper、账户、恢复与日志

固定 WinSW **v2.12.0 / WinSW.NET461.exe**（655872 字节，SHA-256 `b5066b7bbdfba1293e5d15cda3caaea88fbeab35bd5b38c41c913d492aadfc4f`）及 MIT 许可。官方旧资产没有提供独立 digest，本项目通过官方 HTTPS API 获取后记录首次校验值；该二进制 Authenticode 状态为 NotSigned，不宣称独立签名验证。工具、许可、锁文件进入候选清单并在构建/安装/部署时交叉校验；不自动联网更新或下载安装 .NET。宿主须已有 .NET Framework 4.6.1 或兼容更新；实际生产 OS/.NET 仍需验收。

每个服务用独立的 `NT SERVICE\{service-id}` 虚拟账户，XML 不含密码，不回退 LocalSystem；不自动授予交互登录或更改广域 ACL。`acl-plan.json` 列出安装包及 Python 基础运行时的读取、该角色秘密文件的读取、该角色状态/日志/临时目录的修改权限。操作员需按生产 67 配置 ACL，保证其他非授权主体不能改 executable/XML 或读秘密；工具不把当前用户可读等同于服务账户可读。服务账户的网络身份与远程资源权限必须在真实环境验证。

默认 `startup: manual`；仅显式 `automatic-delayed` 生成延迟自动启动。恢复动作依次为 10、30、60 秒后 restart，第四次及以后 none，成功运行一小时后重置；不无限重启、不重启 OS。SCM RUNNING 只证明 wrapper 已运行，不能代替应用 ready/Worker 注册及账目恢复。

安装器从当前原生 CPython 基础安装复制真正的解释器及 python3/python313/vcruntime DLL 至新 venv/Scripts，记录字节数与摘要并执行实际前缀/安装依赖探针；服务不使用多一层进程的 venv redirector。所有服务命令校验这些解释器文件。服务入口仅使用只附着本进程的控制台或新分配控制台，设置隐藏窗口；XML 同时 hidewindow，避免无控制台 Python 被立即终止。存在任何其他附着进程则拒绝，不隐藏或分离调用者的共享控制台。gateway 监督器只启动包内 Provider，清除继承的数据库、代理等覆盖变量，以明确 YAML/JSON 配置为准，并向其独立进程组转发 CTRL+BREAK，90 秒后才终止仍未退出的自有 Provider。其他角色在同一进程执行既有发行入口。

停止先给直接应用进程 CTRL+C，单进程等待 120 秒，先父后子，使 Worker 有机会取消协程、结束有界阻塞操作、关闭 journal 并保留未知提交。超过预算 wrapper 可能终止其拥有的子进程，仍不得将未知执行改为已停止；ComfyUI 不由本工具托管或终止。CLI 每个目标服务的控制等待最长 150 秒，超时保留 pending，不用 `taskkill` 杀任意 PID。真实 SCM/OS 关机的整体等待预算须在管理员测试宿主核验，不从控制台试验推定。

应用 stdout/stderr 放在该角色私有 `service-logs`，按 10 MiB / 8 份轮转；WinSW 2.12.0 的 wrapper 诊断文件不自动轮转，须由生产日志采集/轮转工具单独限制大小和保留（68 待验收），不能将应用 stdout/stderr 的轮转当作 wrapper 日志已轮转；该文件也受私有 ACL 保护。脱敏公共报告只含固定错误码、服务 ID 和状态，不转储 child 输出、完整 config、秘密或内部连接串。gateway 监督器使用最小环境和固定路径，拒绝将继承的 Sub2API/Viper/HTTP 代理覆盖传给 Provider；生产服务账户和凭证文件的权限仍按 67/73 验收。

## 4. 显式命令与保护

候选安装后从其 venv 运行 `payload/scripts/service-deploy.py`：

```powershell
& 'C:/render/install/venv/Scripts/python.exe' -I 'C:/render/install/payload/scripts/service-deploy.py' render --spec 'C:/render/private/services.json' --output 'C:/render/services/edge-a'
& 'C:/render/install/venv/Scripts/python.exe' -I 'C:/render/install/payload/scripts/service-deploy.py' validate --deployment 'C:/render/services/edge-a'
& 'C:/render/install/venv/Scripts/python.exe' -I 'C:/render/install/payload/scripts/service-deploy.py' status --deployment 'C:/render/services/edge-a'
```

`install/start/stop/uninstall` 使用同一 `--deployment`，可用 `--service` 精确选择一项；不带选择器表示本部署全部项。变更前要求现有提升的 Windows 管理员 token；非管理员固定拒绝，不弹 UAC、不启动 wrapper 命令。读取状态不需主动提权。没有日常 developer/bootstrap 自动安装入口。

渲染前先创建各 `state_dir` 和输出目录的父目录，准备好包外 env/JSON/TLS 文件；render 仅创建全新计划目录及各状态目录下的服务日志/临时子目录。实际部署流程为 render/validate → 管理员 install（注册但不启动）→ 按 acl-plan 为此时存在的独立服务账户落实权限 → start → 同时核对 SCM、应用 readiness/Worker 登记和持久账目。各宿主分别部署，跨宿主先完成网络/数据库/TLS/权限验收；SCM 状态不能替代依赖就绪。升级时先按文档 15 排空，停止顺序仅提供本机控制，不自行批准未知 GPU 释放。

操作通过按部署绝对路径命名的全局 mutex 互斥；SCM 操作前先查询实际 ImagePath、账户和状态，必须匹配本部署固定 wrapper、虚拟账户及文件校验。已有同名服务不能覆盖/接管；安装先预检全部目标不存在，部分安装失败只回滚本次已创建且身份仍匹配的服务。同一部署启动按 api、worker、gc、runner、gateway 排序，停止按 gateway、runner、gc、worker、api 反向排序。先停派单，再停 Worker，最后停 API，使 Worker 停止期间仍能回报控制面；此顺序适用于 CLI 批量操作；延迟自动启动本身不建立 SCM 服务依赖，真实开机顺序/恢复和应用 readiness 仍须验收。SCM RUNNING 不等于应用 ready，跨宿主排空由运维核对。卸载仅允许 STOPPED，不删除状态、对象、journal、配置、秘密或发行包；不处理本部署以外服务，不自动强杀。

## 6. 本轮实现与分层记录

固定角色部署工具、真实只读 SCM 查询、专用服务解释器、Provider 监督入口及安装包收集已实现。160 项服务/发行安全专项检查通过；最终完整门禁和精确候选的结果以本节后续记录及汇总 JSON 为准。当前没有注册任何系统服务，也没有请求或启动 UAC。

官方 wrapper 的非提升控制台/核心启动探针在有界等待内没有得到应用 ready，原因未证实；所有探针限于自有 Job Object 并关闭，不能记为 wrapper 生命周期通过。安装候选的应用入口验证另行记录：它直接运行包内服务解释器/入口，不覆盖 WinSW、SCM、服务账户 ACL 或恢复计时。gateway 监督器的真实运行出口同样保持未验证。
