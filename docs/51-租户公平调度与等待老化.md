# 51 · 租户公平调度与等待老化

2026-10-28 补充边界：本文的公平对象是租户/任务服务，不保证多设备的任务分配数均匀。[123 · 多设备模型池](123-空闲资源释放与多设备模型池调度设计.md)核对当前多渠道结构、线上单渠道配置及 Worker 抢领行为，并单独设计全池设备公平；新设备策略尚未实现，不改变本文既有规则和历史验证。

日期：2026-10-24（Asia/Taipei）。本增量实现与本机分层验证通过；本文件不代表完整首版或真实设备验收。

## 1. 范围与不变量

落实 JOB-03、SCALE-04 和 DEV-07/08/13/22/23/26/29/32。旧实现仅按优先级和创建时间领取，不能证明租户公平性。本增量实现租户等份额的预计服务成本调度、等待老化、持久状态和 Admin 解释。五类能力、冻结授权/路由、未知 GPU 占用、当前生成并发、内部重试和唯一客户计量继续执行原约束。

公平状态是调度估计值，不是客户货币、UsageLedger、日额度、真实 GPU 秒数或完成时间预测。只在产生新 attempt 的领取事务内记一次；同请求重放、旧 attempt 投影、空领取、失败领取和事务回滚不增加记录。内部重试的新 attempt 参与一次调度，仍沿用同一 job 的准入和计量。

## 2. 首版固定规则

策略标识为 tenant-service-aging-v1，租户份额为 equal；客户和 Worker 不能传入权重、成本或优先级。Admin 的 jobs:control 继续独占优先级写入，并遵守 CSRF、revision 与幂等。

先排除渠道未应用/未验证/排空、GPU 禁用/保留/占用、缺少相符绑定和当前生成配额不足等候选；领取事务仍重查全部既有硬门禁与规格隔离。任务扫描受全局 500 个未完成任务上限约束；绑定和相关隔离记录每轮最多读取 50,001 条，发现超过 50,000 即拒绝本次仲裁，不静默截断后放行。不因另一个租户不可执行就阻塞其余合格候选，也不借公平性释放 GPU 或降低规格。

普通候选按 max(租户累计虚拟服务毫秒, 全局虚拟时钟) 选择最小的租户；相同时按最近领取的全局序号、最早创建时间和稳定 ID 排序。没有历史记录或长期空闲的租户从当前时钟参与，不追补历史欠账。领取成功时，全局时钟单调推进至该次起点，租户累计值增加本次预计成本，全局领取序号递增并保存到租户记录。

成本优先读取所选 GPU、当前绑定已批准的同 ID 运行画像 warm_p95_milliseconds；没有可信值时，图片类使用 60,000 毫秒、视频类使用 300,000 毫秒。成本限定为 1,000～7,200,000 毫秒。验证任务/显式测试目录没有批准时只使用上述基准。来源和成本写入 job.claimed 审计及 attempt 快照，不能把这些基准当成实测吞吐。

租户内有效优先级为 min(100, 原始优先级 + floor(等待秒数 / 5))，等待从原 job 创建时间计算，未来时间的等待按零处理；相同有效优先级按创建时间及 ID 排序。原始优先级仍为 -100～100，不改写它或每日额度。冷模型无额外负权重；已经等待的任务不会被新高优先级任务永久挤出。

若租户存在已等候至少 300 秒且当前合格的候选，先在这些租户间按最近领取序号轮转，再使用上述租户内顺序。它是避免长服务成本或热请求造成饥饿的明确优先规则；积压较久时不承诺严格按预计 GPU 毫秒比例分配。实际开始时间仍受能力、GPU、并发、维护和 deadline 影响，300 秒不是执行承诺；无法执行和截止时间到达的任务遵循现有状态机。

## 3. 事务与持久化

PostgreSQL 事务级 advisory lock 634720183 仅用于短领取仲裁，先于领取请求、节点、桶、job、GPU 锁获取；不跨媒体、HTTP、文件传输或推理持有。较重的渠道、绑定、规格与容量初选在锁外完成；锁内重新读取任务状态、优先级、deadline、当前并发及公平历史，再排序并逐项执行全部领取硬门禁。锁外观测不构成授权；变为不可执行的候选必须跳过，新出现的候选可在下一次轮询参与。候选排序及实际领取在同一事务内完成，全部 API/Worker 使用同一数据库锁，进程重启不重置公平历史。已有桶→job→GPU 锁顺序保持；桶加锁查询必须刷新 ORM 缓存，避免并发释放后用旧计数覆盖已提交的事实。重复请求也在锁内重查启动标识与旧启动占用后返回。

quota_buckets 增加 dispatch_virtual_milliseconds 与 dispatch_sequence，默认与迁移值均为零、非负，只允许 global/tenant 的 active 桶非零；其他作用域和每日桶必须为零。字段不参与业务配额计算。成功领取同时更新 global/tenant active 桶、attempt、occupancy、当前 job、生成计数、ClaimRequest、审计/outbox。迁移不根据旧 attempt 猜造成本；旧活动任务和其计量保持原事实。

配额桶使用批量补齐和单次有序 FOR UPDATE 读取，按 global→tenant→project→key、period 固定顺序加锁；刷新已有实体并检查目标桶齐全。该优化减少往返次数，不改变准入、终态、取消或重试的配额原子性与数据库持久性。

迁移前停止新领取、备份并核验归档，之后验证既有桶默认值和 42 表恢复演练。已有调度事实时降级拒绝静默丢弃它们。禁止在管理入口直接修改公平计数、虚拟时钟或状态以“插队”。

## 4. 管理界面与兼容
