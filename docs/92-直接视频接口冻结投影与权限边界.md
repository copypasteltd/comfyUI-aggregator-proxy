## 实现与兼容边界

- POST /v1/videos、相同请求键恢复和 GET /v1/videos/{id} 从原 Job.execution.parameters 返回已知 seconds 字符串和 size。格式按整数毫秒精确转换，不读取当前模型默认值、原始输入缺省或重新解析别名；缺失的历史字段省略，已存在但畸形的元数据（含非对象的 execution 或 parameters）返回固定脱敏故障，不猜测或回填。尺寸沿用两至五位正整数字段。内部历史响应上限不扩大原公开视频 120 秒限制和 Workflow 预设。
- 视频状态与 Provider 对齐：admission_pending/queued/leased 为 queued；执行与核对中为 in_progress；成功为 completed；失败、取消、到期为 failed，并分别返回固定 generation_failed/task_cancelled/task_expired 及安全说明。未知 progress 继续省略。Location 与 poll_url 指向该原视频任务，恢复不增加任务或结算。
- 保留直接接口既有安全扩展：task_type、updated_revision、retry、已知 completed_at，以及权限允许时的 artifacts / input。input 仍须 content:sensitive；产物、内容读取和下载仍分别鉴权，不把业务 Key 用于 Admin。直接 job_ 与网关 rc_ 使用各自严格响应契约，不改变外部 ID 或宣称官方严格 Video 类型已兼容。
- 创建、恢复和单任务详情可携带上述安全规格；原生列表保持轻量，不加载 request/execution 或引入逐项查询。视频详情不额外读取当前目录，不增加数据库迁移，不改任务状态、GPU、重试、配额、计量与内容生命周期。
- 代码、脚本与产物在 app；机器契约、文档、版本化证据在 docs。原始青柠视觉保持直接引用，界面未改则不重复替换演示素材。原生运行，不使用 Docker/WSL/VM；只清理本次拥有的测试进程、浏览器和临时资源。

## 客户端使用

提交 JSON 或 multipart 时设置业务 Bearer Key 与 Idempotency-Key。以响应的 Location / poll_url 查询同一任务；同一语义、同一原键重放不随当前目录默认值变化。以下为合成的 202 响应示例，input、progress 和 error 均无可公开的值，因此省略。

```json
{
  "id": "job_aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "object": "video",
  "model": "synthetic-video",
  "task_type": "text_to_video",
  "status": "queued",
  "job_status": "queued",
  "created_at": 1792944000,
  "updated_revision": 1,
  "poll_url": "/v1/videos/job_aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "seconds": "5.125",
  "size": "1024x1024",
  "retry": {"count": 0, "limit": 2, "next_at": null, "last_error": null}
}
```

status 为 completed 时，通过原视频内容入口或有权读取的 artifacts 交付文件；未就绪返回既有 409，其他 Key/租户不存在该资源时返回 404，缺少当前读取 scope 为 403，失效凭证为 401。此处 404 不透露原任务存在性。失败、取消、到期的查询仍为 200，业务 status=failed，error 采用固定原因；排队任务经原生 cancel 动作取消后，查询原视频 URL 可获得同一任务的安全终态。官方严格 Video 类型的 progress/size 限制仍按 [91](./91-多媒体SDK与视频冻结规格.md) 保留。
