# 110 · 输出发布提交不确定与对象清理

2026-10-26（Asia/Taipei）。关联 43/55/61/62、DEV-11/18/23/25/29/31。检查鉴权/内容事务边界时发现 `OutputRepository.accept` 在发布事务抛出异常后将 committed 重设为 false，并在 finally 无条件删除本次存储版本。数据库实际已提交但确认丢失时，ObjectRecord/OutputUpload 已持久引用该版本，清理会删除有效产物。输入素材已有重新查询保护，输出尚未使用该边界。本专题先固定行为，再以真实 PostgreSQL 的提交后故障复现。

## 固定规则

1. 本次写入的精确 object_key/version 不等于可随意删除的临时文件。COMMIT 报错不证明事务回滚；不能删除已经被数据库发布的版本。
2. 发布未被本次调用明确确认时，在新的短事务先锁定同一上传记录，等待原发布事务结束，再按精确 key/version 查询 ObjectRecord。不能只用普通快照的“暂未看到记录”推断可以删除。只有查询成功并证明无引用，才允许删除该版本；查询失败或查到引用均保留。
3. 数据库会话在调用对象存储 delete 前结束，不持有数据库连接/事务跨外部 I/O。只删除本次版本，不删除同 key 的其他版本或既有成功产物。
4. 清理是尽力操作；查询/删除异常不覆盖原发布错误，也不把有效重复上传的已验证响应改成清理失败。保留孤儿对象供既有核对/GC 流程处理，不扩大重试或扫描预算。
5. 日志只使用固定 output_cleanup_deferred_pending_publication_verification 标记，不含异常正文、对象路径、SQL、凭证或客户内容。
6. 原上传授权、摘要/媒体检查、当前租约/fencing、不可变清单、唯一发布与唯一结算继续适用。重复提交只恢复已有上传/结果，不产生新生成任务。

## 验证出口

- 真实 PostgreSQL 已提交 ObjectRecord/OutputUpload 后，在 after_commit 注入确认丢失；原文件及引用保留，正常重传/完成能下载正确字节并只发布/计量一次。
- 同样的确认丢失后，新的查询失败仍保留对象；原确认丢失异常不被替换。
- 真正提交前失败回滚：查询可用时删除精确未发布版本；查询失败时保留，数据库不发布成功。
- 清理删除失败不掩盖原发布/完整性错误；健康重复上传不受孤儿清理错误影响，原已发布版本不被删。
- 存储 delete 时不占用测试数据库连接；固定日志不暴露故障正文。

测试使用真实项目测试 PostgreSQL、原生文件存储与合成 PNG。提交后事件注入是数据库提交结果不确定的可控复现，不是物理网络/真实 S3 故障验收。真实六类 Workflow、10～20 台、历史鉴权/审计/CI 根因和生产完整验收保持开放。
