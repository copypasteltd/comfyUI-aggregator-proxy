# 137 · 持久模型池与全局设备均衡

本增量实现F-41和文档123的设备公平层，已部署后端137.1/静态136.1。本地38项原生专项、1,695项兼容回归、Admin类型/构建、5组合成页面及3组线上页面检查通过。新功能pending-test，尚未签收真实多卡或10～20台容量。租户公平仍先选任务，设备公平随后选该任务的物理GPU；不改变已有任务状态、计量、未知执行保护或Worker协议。

Admin模型映射增加`routing`，默认`{"policy":"first_ready","weights":{}}`保持既有抢领。管理员可显式选择`balanced_ready`；权重以物理`gpu_`ID为键，正整数1～1000，省略为1，最多沿用100个映射渠道的设备集合。不同渠道指向同一GPU只算一份。权重只是相对分配份额，不是并发数、超时、价格或质量。变更映射继续下架并要求原有逐渠道/逐发布运行批准，不把相似Workflow合并。

新任务在受理事务中冻结不可变池ID；池ID摘要覆盖模型、release、全部渠道到GPU的映射及权重。历史任务迁移为`device_pool_id=null`，继续原策略；改变模型或权重生成新池版本，已有任务不扩展路由。池内配置不变、历史保留，普通进程/Worker重启不清零公平计数。新增池版本各成员从相同相对信用基线开始；离线或忙卡不追赶长期缺席期间的历史任务。

设备选择采用持久平滑加权轮询：在合格且空闲的物理GPU中，各自信用加权重，最高者获选（平局按最后分配序号/GPU ID），获选信用扣除本轮合格总权重。未就绪成员信用归零；已分配次数与当前信用分开保存。等权持续同等就绪时100次分配计数差不超过1；不承诺异构设备完成数相同。冷缓存不改变权重。

使用既有PostgreSQL全局领取事务锁进行等价全池裁决，无新增offer有效期或网络往返：任何Worker请求都查询原任务冻结路由中的全部候选，只有获选设备所属Worker可接受；其他Worker返回空并且不推进信用、次数、配额或attempt。获选Worker在同一事务中再次通过现有硬门禁，随后将公平信用/次数、attempt、GPU占用、配额和幂等领取结果一起提交。任何失败/回滚不消耗公平分配；重放不重复计数。选择和提交间不执行HTTP/GPU操作。健康但尚未轮询的目标最多受已有心跳新鲜度约束，需单独观测延迟，不新增任务重试。

候选同时满足：原受理授权冻结渠道、同租户/项目/发布、渠道当前同步/验证、目标GPU对应运行批准、新鲜Worker启动/容量、三维/音频能力、无当前或旧启动未知GPU占用、无维护保留、无OOM排除/规格隔离，以及新鲜ComfyUI可达且运行/等待队列均为零。实际领取仍重查；未选中、不可达、未知队列、失联、排空、配置漂移、冷缓存、外部入队等不允许扩大旧路由或重跑未知任务。

新增只读Admin池统计仅限`models:read`，提供当前池版本、各物理GPU权重/分配次数/序号；不返回业务提示词、凭证或客户任务。业务API仍提交一个公开model，不接受客户指定GPU或公平计数。数据库增量先原生验证和备份，再以兼容向前方式发布；有已使用均衡池时拒绝降级抹除公平历史。

启用均衡后，应用恢复也必须使用理解`device_pool_id`的新版本；旧调度API不能解释冻结池，不能作为已接收均衡任务的回退目标。本轮发布工具仅在没有均衡模型/任务时允许恢复旧API，数据库不回退。

## 线上交付与使用

在现有Admin“模型与路由”编辑映射，选择同一release已逐卡批准的渠道，设置“就绪设备加权均衡”及各物理GPU权重，保存后重新发布。原业务调用继续提交公开model，无需指定设备。点击“设备分配”查看当前池版本及累计分配；选择原策略的模型显示说明，不伪造零均衡历史。
