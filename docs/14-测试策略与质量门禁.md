# 14 · 测试策略与质量门禁

验证的目的是证明授权、并发和故障行为。应用已在 app 持续实现并执行原生 PostgreSQL、HTTP、浏览器和协议回归；本文件规定完整门禁，具体通过范围以文档 17 及可核对证据为准。未测真实设备、存储与发布条件不能由静态或协议测试替代。

## 3. 故障注入方法

可控代理/原生测试 HTTP 进程模拟连接建立失败、响应已写前断线、请求已处理后丢响应、延迟、分片中断和重复回调；不能只用抛异常覆盖“实际提交后客户端不知道”的场景。Worker 在 journal commit、POST、prompt_id 保存、GPU 释放、分片确认和 complete 回执各设测试断点，真实停止测试进程后验证恢复。

并发测试至少使用两个独立进程/数据库连接，以 barrier 对齐竞争时刻，断言数据库最终不变量而非依赖 sleep 顺序。测试时间通过服务器时钟适配或可控时间推进，不通过修改系统时钟影响用户环境。压力测试限流并可停止，不向生产渠道发合成负载。

取消测试区分尚未执行、GPU运行、编码、上传、核对和已终态。不能以 `/interrupt` 200 为“指定任务已停”的唯一断言；独占实例能力与实际 queue/history/进程事实一并验证。

## 5. 证据格式

每次验证在 `docs/evidence/<run-id>/` 保存脱敏报告：commit/依赖锁 hash、契约版本、数据库 migration、Worker/ComfyUI/GPU/驱动/Workflow、节点数和真实/模拟标记、命令与时间、断言结果、性能分位与资源量、失败/skip/限制、清理结果。真实文件可放受控证据存储并记录 hash，不能把私有素材放 Git。

发布签收必须逐项列未完成设备/能力/网关联调，不能仅引用本目录的静态校验记录。文档工具输出只声明静态范围，服务上线质量要由上述运行证据支持。

规格隔离专项按 [46](./46-生成失败归因与规格隔离.md) 执行：类型/消息伪造、当前队列仍运行、输出仍变化、媒体拒绝与传输故障必须分别验证；真实 PostgreSQL 覆盖重复回执、窗口、迟到结果、GPU/发布/规格隔离、201 条隔离队首后领取健康规格及并发恢复/失败。验证绕行只能由显式管理验证产生，并检查旧 boot/渠道版本/清单/对象/时间证明拒绝。浏览器检查使用实际生产构建和 HTTPS 会话，隔离数据/写回显式合成；每次 finally 关闭自建 context/browser。原生组合链路及模拟 OOM 不替代真实 GPU OOM、Workflow 质量或 10/20 台实机验收。
