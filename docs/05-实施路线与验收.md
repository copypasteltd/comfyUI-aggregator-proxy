# 05 · 实施路线与验收

## 1. 实施判断

该方案可行，10～20 台设备的数量不是主要难点。主要工程量在于工作流与硬件画像、Sub2API 的实际 Provider 适配、长任务恢复、生成文件和账单的一致交付，以及首版可视化 Admin。

建议按端到端闭环逐步扩展。先完成小规模闭环是排除接口和环境问题的实施步骤，最终仍需覆盖五类能力和目标节点规模。

需求基线 v0.2 将可视化 Web Admin 列为首版必交。渠道地址、Workflow/模型管理、全局及各渠道实时队列必须有可实际操作的页面，不能推迟为首版上线后的可选补充。

需求基线 v0.3 进一步将多业务 API Key、独立权限/限额和内容隔离纳入同一首版。Key 由 Admin 管理，用于对外生成及内容 API；业务 Key 不用于后台登录。

开发设计基线 v0.4 补充 [09](./09-开发总纲与强制约束.md)～[16](./16-开发任务分解与交付清单.md)、机器契约和离线文档工具。下面的产品验收保持有效，工程工作包依赖与出口以文档16展开；本文不代表任何运行验收已通过。

| 阶段 | 主要产出 | 完成条件 |
| --- | --- | --- |

| M2 五类工作流与能力管理 | 五类发布包、参数/素材/视频适配、硬件画像；Admin Workflow/模型管理、Key 能力限制与内容目录 | CAP-01～05 有真实样本；未验证能力不能发布，Key 模型/Workflow/渠道限制与内容过滤生效 |
| M3 Sub2API 完整适配 | 模型/图片/视频路由、公共任务/身份绑定、计费归属；Admin 发布/回滚与外部 Key 映射、下载策略 | 固定实例端到端通过；客户身份/内容不混用，下载/转存遵守 Key 策略，重启/停止轮询不漏单漏结算 |
| M4 10～20 节点、实时后台与恢复 | 公平调度、资源锁/恢复/上传；实时后台与审计；多 Key 并发限额、权限变更/撤销、计数恢复 | 20 Worker 协议与管理面负载通过；无跨 Key 越权、额度竞争或轮换重置，按实际规模做硬件验收 |
| M5 首版对外交付 | 原生部署包、可操作 Web Admin/多 Key/内容管理、运维/备份恢复、监控/灰度与回滚记录 | 全部门禁含 ADMIN-TEST-01～16、KEY-TEST-01～12 完成；未测性能/能力不对外承诺 |

M2 与 M3 可在接口冻结后独立推进，但共享同一个 job/asset/计量模型。New API 适配放在以上主路径稳定之后，不影响 Sub2API 优先顺序。

当前不足以给出可信的固定交付工期：设备环境一致性、自定义节点质量和 CAP-05 是否有可用模型会显著影响周期。M0 后可按发布包数、Sub2API 改动量和真实故障演练范围估算人日，避免只按“写一个转发接口”报价。

## 6. 20 节点与负载验收

| 编号 | 范围 | 通过条件 |
| --- | --- | --- |
| SCALE-01 | 20 Worker 注册/心跳/断连/重连 | 无身份冲突、活跃租约不被旧 boot 覆盖、恢复后不抢占旧任务 |
| SCALE-02 | 同一 GPU 多实例、重复领取并发、生产实例混入人工任务 | 未经批准永远只有一个生成槽位占用；20个实例不等同20块GPU；发现未知prompt先隔离/核对，不抢占或清空整队列，人工使用必须先排空 |
| SCALE-03 | 异构能力和显存画像 | 低显存/缺模型节点不接到不适配任务；视频画像按帧数/尺寸匹配 |
| SCALE-04 | 多租户混合图片与视频 | 公平份额/优先级权限生效；等待老化有效，不被热模型永久饿死 |
| SCALE-05 | 500 未完成任务的控制面试验 | 提交/查询/调度达成约定目标，超上限明确拒绝；不要求一次真实生成 500 条 |
| SCALE-06 | 20 Worker 同时上传/续传 | 上传并发、云端带宽与磁盘预算受控，控制 API 不被文件流阻塞 |
| SCALE-07 | 长稳运行与模型切换 | 无持续显存/内存/磁盘增长，错误可隔离，任务与结算账目完整 |

协议模拟允许验证状态、租约和并发竞争，不能代替真实 CUDA 显存、视频质量或网络吞吐。建议先接入 10 台真实设备，再扩到实际可用的 20 台；如果只完成 10 台实测，只能声明“20 节点协议测试、10 台真实运行测试”。实际计划对外使用 20 台时应补齐 20 台实测记录。

控制面目标沿用文档 01：已就绪素材的提交/查询 P95 小于 1 秒，有匹配空闲节点时派出租约 P95 小于 5 秒。负载报告须包含请求速率、查询频率、租户数、任务混合和持续时间；只报一个 P95 数字无效。

## 7. 故障恢复验收

| 编号 | 故障注入 | 必须证明的行为 |
| --- | --- | --- |
| FAIL-01 | 接收提交后立即断开客户连接 | 任务可按稳定 ID/幂等键恢复查询，无第二次无意生成 |
| FAIL-02 | `/prompt` 已接收但响应丢失 | 原 prompt 被核查继续，不直接重复 POST |
| FAIL-03 | WebSocket 断开 | HTTP 核查与重连可恢复原任务，进度未知不等于生成失败 |
| FAIL-04 | Worker 杀进程再启动 | journal 与真实 ComfyUI 队列核对后恢复，不抢先领取新任务 |
| FAIL-05 | Windows/ComfyUI 重启，history 消失 | 使用进程、journal 和输出证据分类，不单凭空 history 重跑 |
| FAIL-06 | 私网中断，旧 GPU 仍运行 | 暂停派单、隔离未知占用；旧租约无法提交新终态 |
| FAIL-07 | 租约过期后的迟到结果 | 旧 attempt 不能覆盖当前结果或触发第二次收费 |
| FAIL-08 | 分片上传中断 / 上传凭证过期 | 文件从本地恢复回传，不重新耗 GPU 生成 |
| FAIL-09 | 云存储成功但云端回执丢失 | 检查现有对象后幂等完成，不丢成果、不重复计费 |
| FAIL-10 | API/调度/数据库进程重启 | 已确认任务从持久状态恢复；事务失败不产生半领取 |
| FAIL-11 | 客户取消与成功回报并发 | 唯一终态；取消确认前 GPU 不错误释放 |
| FAIL-12 | 重复结算事件、外部账本暂不可用 | outbox 重试且账本幂等，异常可检索、可对账 |
| FAIL-13 | 节点 OOM、磁盘满、缺模型 | 隔离或明确拒绝，避免无限自动重试和静默降质量 |
| FAIL-14 | 云端整机灾难恢复演练 | 从备份恢复到约定恢复点；不混同于普通进程重启的持久性 |

上述故障测试是后续实现验收要求，本轮没有对真实设备进行故障注入。

## 9. 容量估算方法

以下是算式示例，不是对现有设备的性能预测，MB/GB 使用十进制单位。

### 9.1 GPU 吞吐

对同一个已测试工作流，单节点每小时能力约为：

```text
单节点每小时任务数 ≈ 3600 × 综合可用系数 / 平均占用GPU秒数
总能力 ≈ 所有能执行该工作流的节点能力之和
```

| 假设场景 | 10 个合格 GPU，系数 0.7 | 20 个合格 GPU，系数 0.7 |
| --- | --- | --- |
| 每张图占 GPU 120 秒 | 约 210 张/小时 | 约 420 张/小时 |
| 每条视频占 GPU 900 秒 | 约 28 条/小时 | 约 56 条/小时 |

图片和视频不能同时分别达到同一 GPU 池的全部吞吐。若 20 GPU 的每小时预算为 `20×3600×0.7=50,400 GPU秒`，300 张图片加 20 条视频需要 `300×120+20×900=54,000 GPU秒`，会持续积压。按能力子池分别计算，并计入模型切换和维护。

调度日志分别统计 GPU 服务时间和端到端时间。排队、CPU 编码或上传不应全算成 GPU 忙碌，但可能限制最终交付速度。

### 9.2 网络

```text
理想传输下限秒数 ≈ 文件MB × 8 / 有效Mbps
```

200 MB 视频经 20 Mbps 上行，理想下限约 80 秒。20 台同时上传各 200 MB，若共同瓶颈为 100 Mbps，全部 4,000 MB 的理想完成下限约 320 秒；协议开销、中继、丢包和并发会进一步增加时间。

因此必须同时测单台上行、组网直连/中继、云端汇聚带宽和对象存储直传。不能只测试服务器 ping 或单个小文件。

### 9.3 存储和下载成本

```text
在线输出存储GB ≈ 每天成功任务数 × 平均文件MB × 保留天数 / 1000
月下载GB ≈ 每天成功任务数 × 平均文件MB × 每成果平均下载次数 × 30 / 1000
```

按当前八小时云端输出保留期，若每天均匀生成 500 个产物、平均 80 MB，稳定窗口输出约 13.3 GB；加入 30% 临时/重试余量约 17.3 GB，另算突发流量、输入、备份和未完成上传。实际容量按峰值实测，不把均匀流量估算视为磁盘保证。每成果下载一次，月下载约 1,200 GB。

价格评估要同时记录云主机、数据库、存储容量/请求、下载流量、组网服务、Windows 电力与维护成本。价格待选定厂商、地域和实际用量后核算，本轮不虚构固定月费或单次利润。

## 10. 设计决策记录

| 决策 | 建议 | 原因及复议条件 |
| --- | --- | --- |
| 队列位置 | 云端数据库权威队列 | 统一 20 节点公平性和恢复；规模实测不足时再加 Broker |
| 节点通信 | Worker 主动连接/领取 | 降低入站和 NAT 依赖；管理面可经私网运维 |
| 接入优先级 | Sub2API 优先、自有 Provider 适配 | 已确认偏好；零改动方案无法默认满足全部目标 |
| 公共协议 | 图片兼容 + 图片异步扩展 + 视频冻结协议 + 原生 jobs | 避免将不存在的统一多参考异步标准当承诺 |
| 文件位置 | 云端私有对象存储 | 减少控制主机带宽/磁盘压力；全流经主机时重新压测 |
| GPU 并发 | 每物理 GPU 默认 1 | 稳定画像先行；并行需专门显存/时延与隔离测试 |
| 工作流权限 | 固定版本白名单 | 可预测耗时、质量、依赖和输出，不公开任意图执行 |
| Admin 范围 | 首版必须交付可操作的图形后台 | 用户明确要求管理渠道、Workflow、模型与实时队列；API 与日志作为配套 |
| 多 Key 范围 | 首版 Admin 管理业务 Key，对外生成/内容鉴权 | 用户明确确认用途；管理账号、Worker 和网关身份独立，按项目/Key 隔离内容 |
| Key 下载策略 | 默认鉴权代理，可显式允许短时签名 URL | 确保内容访问控制有实际边界；网关转存、客户端兼容和带宽分别验收 |
| 渠道队列口径 | 中央待分配 + 共享候选 + 唯一已分配 + 本机观测 | 保持全局公平调度，避免跨渠道重复计数和预塞 ComfyUI 长队列 |
| 部署 | 原生服务 | 遵守本地禁用 Docker/WSL/虚拟化环境的约束 |
| 收费 | 单一客户账本，成功交付结算 | 重试和内部资源浪费不重复转嫁客户；对账可恢复 |

## 13. 首版 API Key 与内容访问验收

通过浏览器创建/配置多个业务 Key，再使用实际 HTTP 客户端调用对外接口核对效果；业务 Key 不得用于后台登录或管理 API。完整规则与需求映射见 [API Key 专项设计](./08-APIKey鉴权与访问控制.md)。沿用既有五类能力、下载、状态机、唯一账本和无本地虚拟化约束。

| 编号 | 操作/场景 | 必须证明的行为 |
| --- | --- | --- |
| KEY-TEST-01 | Admin 创建两个以上 Key，命名、设置策略、停用/恢复、撤销/归档 | 页面和实际调用均生效；首次显示秘密、后续脱敏；独立 key_id 与历史关联保留，已撤销不可恢复 |
| KEY-TEST-02 | 无 Key、伪造 Key、用业务 Key 访问 Admin/内部 API，低权限后台账号修改 Key | 401/403 按身份边界拒绝，不匿名放行、不扩权；生成/任务/内容接口均受鉴权，拒绝不耗 GPU |
| KEY-TEST-03 | 图片 Key 调视频/原生 jobs、越范围模型/Workflow/渠道/规格，切换公开别名版本 | 所有入口统一检查，模型列表不泄露未授权能力；租约只到允许渠道，版本限制不被别名绕过 |
| KEY-TEST-04 | 同项目独立 Key 和另一租户互查/引用内容，再显式授予同租户只读共享 | 默认隔离；列表/计数/游标/详情/下载/引用均无泄漏；共享仅授予声明动作，标签/project_id 自填不能改归属 |
| KEY-TEST-05 | 并发触发 RPM/突发、每日任务、未完成数、生成并发和图片/视频额度；重放幂等请求 | 上限无并发绕过，429 含具体原因/恢复条件；HTTP 重试仍计频率但不重复预留任务，内部重试不重复扣资源，项目/租户总限额有效 |
| KEY-TEST-06 | 有效期、IP 白名单、伪造转发头、权限收紧/停用/撤销后立即请求，测试旧缓存与长等待结果 | 按当前策略/可信源 IP 拒绝；旧缓存不放行，返回受保护结果前复核，权限服务故障不退化为无限额 |
| KEY-TEST-07 | 同一逻辑 Key 轮换，默认立即失效/显式短重叠；丢失创建/轮换响应后重试 | 旧凭证按窗口失效；新凭证可访问原授权内容，幂等/用量不断档；响应重放不再次披露秘密，独立新 Key 不自动继承内容 |
| KEY-TEST-08 | 内容目录按项目/Key/模型/Workflow/标签/时间过滤，查看用量/拒绝记录、受控删除 | 筛选与源对象权限一致；敏感提示词/原图需额外权限；活动引用拒绝/延迟删除，不改历史任务；审计无明文 Key |
| KEY-TEST-09 | 两种下载模式的 GET/HEAD/Range/预览、签名刷新、同步 Base64 与网关转存，期间撤销 Key | 代理每次鉴权且不重定向绕过；无下载权限不内联交付；签名模式明确可用至到期，已开始流不假报追回；客户端与带宽有实际记录 |
| KEY-TEST-10 | 不同 Sub2API 客户通过同一网关业务凭证调用；测试伪造/缺失声明、同名 Key 与直连映射 | 可信 issuer/外部引用决定主体，内容/限额不混到共享 Key；无映射拒绝，显式统一主体才共享；无重复客户余额账本或扣费 |
| KEY-TEST-11 | 停用 Key 时有排队/执行/上传任务，再由 Admin 显式阻止或取消旧任务 | 后续调用禁止但默认已有任务可收尾/结算；显式处置可追踪，未确认停止不释放 GPU，旧路由/质量不静默变更 |
| KEY-TEST-12 | 重启鉴权/任务/数据库服务，两个管理员并发改策略，重复创建/轮换，并跨每日账期 | 凭证摘要/策略/计数/预留/审计恢复；版本冲突与管理幂等有效；按 Asia/Taipei 账期计数，重启/轮换不重置或放开限额 |

验收保留脱敏策略前后版本、Key/项目标识、HTTP 请求/响应、job/operation ID、配额计数和审计证据，不把真实秘密值写入报告。控制面模拟能验证并发和状态，实际网关转发、文件下载和权限边界必须用真实链路验证。

以上为首版开发验收要求；本轮未创建真实 Key，也没有实现或运行鉴权/内容服务。
