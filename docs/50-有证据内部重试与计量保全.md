# 第 50 增量：有证据内部重试与计量保全

开始：2026-10-23；跨日验证：2026-10-24（Asia/Taipei）。对应 DEV-06～15/20/22/23/25～32、WP-01/02/04/05/06/09/11/13/14。先冻结语义与机器契约，再修改实现、迁移、页面及验证；本轮实现、验证和候选在下文分别登记，完整首版仍未签收。

## 1. 适用范围与冻结行为

补齐既有 retry_wait 状态的持久内部重试。首批可重试分类是 preparation_transport_failure：Worker durable journal 仍为 accepted、从未写入提交意图，遇到明确传输连接/超时/协议读失败，或 HTTP 408/429/500/502/503/504。普通配置错误、输入摘要错误、路径/模型/环境问题、OOM、输出不合法及旧 Worker 的通用 preparation_failed 不自动重试；已到 submit_intent/posting 或拥有 prompt 的失败保持现有确认/核对流程。不得把“传输错误”一概推断成 ComfyUI 未提交。

云端独立核验：当前有效租约，job 处于 leased/preparing，attempt 没有关联提交 ID/prompt，执行停止确认与证据摘要存在，且本轮生成槽已明确释放。仅凭 Worker 错误代码不扩大条件。已取消请求、验证样本任务、截止时间不足、重试次数耗尽或证据不足，不安排自动重试；未知执行继续保留 occupancy/核对，不生成新 attempt。

每个业务 job 最多安排 2 次内部重试，即最多 3 次上述可确认的准备尝试；服务器退避分别为 5 秒、15 秒，必须在原 deadline 前到期。count 表示已安排重试次数，不是客户重新提交次数。内部重试保留同一 job、逻辑 Key、准入自然日、request/execution fingerprint、实际 seed、冻结 Workflow/路由和输入引用。重领取仍使用当前租户/项目/Key 的并发上限与节点/渠道/GPU/环境健康检查；遵守文档 08 的既有已接收任务规则，不把 Key 轮换或停用当成隐式取消。

后续分类以 [82 · 确认失败重试与跨 GPU 约束](./82-确认失败重试分类与跨GPU约束.md) 为准：完整当前 prompt 停止证明、原冻结路由内另一已批准物理 GPU 和共享预算满足时，允许一次 OOM 重试。下文实施数字保留为第 50 增量历史；不能据此取消新扩展，也不能把普通执行错误或未知提交提升为可重试。

## 2. PostgreSQL 事务与恢复

jobs 增加 retry_count（0～2）、retry_after、retry_error_code 和 retry_source_attempt_id。来源 attempt 以同 job 复合外键约束；retry_wait 必须有正次数、待执行时间、明确来源和固定原因，且没有 current_attempt。其他状态不得残留 retry_after。增加有界 due 索引。迁移先通过原生备份与归档验证；若旧库存在没有证据的 retry_wait，不自动编造来源。降级拒绝丢弃已有重试事实。

失败事件的同一事务中按原有桶→job→GPU→attempt 锁序释放生成计数/occupancy、关闭旧 attempt、记录 retry_wait 和下次时间、清空 current_attempt、保存 WorkerInbox 幂等回执及审计/outbox。unfinished 与每日资源预留继续保留，不重复增加 daily_jobs，不写终态 UsageLedger/网关结算。重复或并发的同一事件只能得到同一结果；迟到的不同事件及旧 lease/fence 不能推进新尝试。

Runner 每轮有界领取到期项，再取得桶/job 锁并重查；只有来源 attempt 已关闭、生成已释放、没有提交关联/prompt、没有该来源 occupancy 时才转 queued。多个 Runner 并发与重启只提升一次；GPU 可能已被其他任务占用，不据此释放其他 occupancy。未到时间不得领取。retry_wait 截止时间到达时按未执行过期一次结算；取消与到期/提升/领取竞争由同一事务序列化。任何不完整恢复证据保持等待/核对，不通过直接改表“解卡”。

## 3. API 与 Admin

原生 job、授权 job 集合及 Admin 增加可选 retry 元数据：count、limit=2、next_at 和 last_error；机器契约为 job-retry.schema.json，旧持久响应允许缺少该扩展。等待重试期间不伪装为终态错误，旧尝试和原因在详情中保留。OpenAI 图片/视频和固定 Sub2API 继续沿用现有异步状态投影与单一账本，不增加客户收费。

Admin 任务列表/详情显示内部重试次数、服务器下次时间及安全原因，人工“关联新任务重试”仍只对既有终态执行并重新准入计量。未领取的 retry_wait 可取消和调序，保持 CSRF/revision/幂等与 jobs:control 权限。全局快照 states 中明确显示等待重试；它属于 unfinished，退避期间不加入可立即领取的 queued/渠道共享候选，也不算当前分配渠道。按渠道筛选需能查看该冻结路由的待重试项，并注明候选尚未到期。

前端继续遵守隐藏/退出/卸载清理，不新增持续倒计时轮询。缺少新元数据的旧响应显示可解释的兼容值，不能制造下一次执行时间。

“可再次分配时间”表示服务器最早允许重新进入分配池的时间；实际领取仍等待并发、健康和 GPU 资源满足条件。首版内部重试上限和退避由冻结协议确定，Admin 不提供任意修改重试时间、来源或数据库状态的入口。取消后 next_at=null，必需的可空元数据不能被后台详情的空值过滤省略；保持 OpenAPI 字段形状及输入内容的既有授权边界。
