## 3080 启动修复与未知提交

[设备恢复回执](evidence/2026-11-04/catalog-device-recovery-151.json) 记录本轮远程管理重新可用，3080 连接具备管理员权限。初次检查没有 ComfyUI 主进程或 8188 监听；原 Worker 服务仍运行。原启动任务返回退出码 1。

独立后台捕获定位到 Windows PowerShell 5.1 的 `NativeCommandError`：Python 写到标准错误的一条正常 Alembic INFO 日志，在合并重定向且 `$ErrorActionPreference='Stop'` 时提前终止启动。修复仅对原生 Python 调用局部使用 `Continue`，随后恢复原偏好；原有 `$LASTEXITCODE` 非零检查、Python 参数、环境和监听规格均保留。[可审查补丁](../app/ops/windows/comfy-launcher-native-stderr.patch) 对摘要匹配的原脚本通过适用检查；设备保留原脚本备份。未替换云端应用或 Windows Worker。

修复后原 SYSTEM 启动任务持续运行，ComfyUI 主进程监听 `0.0.0.0:8188`，原 Worker 服务进程身份保持。任务计划中的 `267009` 是运行中状态码，不是本次失败退出码。没有创建浏览器标签页，也没有关闭用户已有的页面或程序。

The startup fix preserves Python stderr logging and still rejects a nonzero process exit. It restores the existing native startup task, with the original launcher backed up and both script hashes recorded. It does not resubmit a generation job.

原验证尝试的 journal 仍为 `posting`，尚无 `prompt_id`；云端仍为 `reconciling`。重启后的 ComfyUI 队列为空、历史为空，不能据此证明旧尝试未被接收或可以安全重提。因此保持原 GPU 占用和提交记录，不直接修改生产表、不释放占用、不复制任务到其他节点。该问题是设备/执行恢复待处理，不能算作源 Workflow 缺模型的排除理由。

现有恢复协议可以恢复找到的原 prompt，或经摘要验证的本地产物；单纯 `absent` 返回需要关注且不允许重提。若旧实例的证据无法找回，仍需补齐具有可靠停止证明、原尝试身份校验、持久记录、审计与幂等的受控关闭流程，并验证并发和旧回执拒绝。该停止确认路径尚未实现或验收，本次不以临时脚本伪造 Worker 事件来关闭任务。完成该恢复后，才继续同一 GPU 上的五项验证。
